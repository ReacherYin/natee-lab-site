harness × loop × memory engineering

收到開發任務就派給 agents，透過 AI 工程架構來達到可靠的實作：一副可靠的框架（harness）、一組會自己收斂的迴圈（loop），和一份會愈用愈準的長期記憶（long-term memory）。

#natee-lab

Harness engineering

把 agent 圍進可靠的工作框架
  • 交辦時給 agent 一份寫清楚的規格和驗收清單；它回報的是固定格式的結果——做完了沒、卡在哪，系統直接看得懂，不用人猜
  • 修不好最多重修兩輪就停；做太久或中途斷線，系統都知道怎麼收拾，不會掛在那裡等人救
  • 每一步重跑都安全——做過的事都有記號，不會重複派工、重複留言

Loop engineering

讓迴圈自己收斂
  • 一張 issue 開出來，從寫程式、審查、補文件到合併，整條路自己走完，人不用盯
  • 中途出事——測試失敗、審查斷掉、程式碼衝突、票漏了沒派——系統定期巡一遍，自己撿回來繼續
  • 票之間可以標「先做完那張、再做這張」，前一張合併，下一張自動開工
  • 敢讓它全自動的原因：每一輪都要過測試和驗收條件，過不了就不往下走

Memory engineering

讓經驗留在系統裡
  • 每做完一輪，agent 要寫下這次做了什麼、哪裡跟當初講的不一樣、踩到哪些坑——spec 寫在前、reality 補在後，同一份文件。下次派工，它讀的就是這份
  • 文件之間互相連著、README 當索引，整個 docs/ 是一張知識圖譜（knowledge graph）：先找到一篇，再順著連結展開，不用整包讀進 context
  • 開新功能前先查有沒有做過類似的，能重用就重用，也看看上次怎麼出錯——這一步不靠向量比對（RAG），是 agent 拿關鍵字和索引自己找（agentic retrieval）；找什麼、讀多少進 context，就是 context engineering
  • 文件跟程式碼在同一個 PR 裡合併（原子性），不會有「程式改了、文件還停在舊版」的狀況
139issues → merged prs, hands-free

整個軟體工作流只專注於兩件事：清楚的需求描述、確認成果是否合格；剩下的都交給自動化流程。
